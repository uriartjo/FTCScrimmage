Update — a harsher second pass, checked against real bytecode

Everything in this section was found by decompiling the real v3.0.0 jars a second time with the specific goal of finding what the first pass missed, compiling the actual repo against those jars, and reading the Huskie Physics "Shoot-on-the-Move" PDF cover to cover against what's actually in Shooter.java. Two of the four findings below are now fixed and compile-verified; two are disclosed, not fixed, because fixing them safely needs real hardware measurements, not more code.

⚠ Finding A — every OpMode NPE'd on init(), understated in the original TODO list

ShooterTeleopBase.init() called follower = Constants.create(hardwareMap) (a one-line stub returning null) then immediately follower.setPose(startPose) on the next line — a guaranteed NullPointerException the instant any of the 11 OpModes was initialized on the Driver Station. This is the exact bug shape "Landmine 4" below caught in one auto file, except it was live in literally every OpMode, and the original TODO list filed it as an inert to-do rather than "nothing in this codebase can be touched on a Driver Station today." Status: partially fixed — see Constants.java below.

⚠ Finding B — "shoot on the move" was never actually implemented

Read the full Huskie Robotics 3061 physics note this migration was said to reference. Its entire content is a specific recipe: characterize the shooter → pick a static shot map → subtract the robot's velocity vector from the launch vector → rotate into the robot/turret frame. Shooter.java's calculateTargets/flywheelSpeed/hoodAngle/calculateTurretTarget only ever use the robot's static position and a quadratic regression on straight-line distance — there is no reference anywhere in this codebase, old or migrated, to follower.getVelocity() or any robot vx/vy. That's steps 1–2 of the PDF's recipe (a static shot map), not shoot-on-the-move. Every shot taken while translating will miss in the direction of travel, exactly the scenario the cited paper exists to fix. Status: implemented this pass — see "Shoot-on-the-move" below. Not yet safe to switch on: the algorithm is real and unit-tested, but its physical calibration constants (flywheel radius, hood angle range) are still placeholders.

Finding C — Red_18Ball_lastrow's disclosed mirror inconsistency is a real 2.5″ field-geometry split, plus a stale comment

The file's own javadoc already discloses that it mirrors most poses with a local m(Pose) helper using a 144.0-inch field length, while four gate poses use RobotConstants.mirror()'s 141.5-inch length — a real, live 2.5-inch difference in where the red-side gate waypoints land relative to every other pose in the same path, not just a stylistic quirk safe to leave. Separately, m(Pose)'s own comment claims it "only mirrors the heading when a non-zero heading was explicitly set," but the code beneath it has no such branch — it unconditionally computes π − heading every time. Harmless today by luck of the specific control points used, but a maintainer trusting the comment would be wrong. Status: not fixed — both disclosed in code, worth a deliberate decision on which field length is actually correct before red autos are trusted near the gate.

Finding D (self-critique) — the original Landmine 1 write-up missed that v3's own mirror utility has a different bug

Decompiling PoseFactory.mirrorX's bytecode (not done in the first pass) shows it computes withHeading(-heading()) for the mirrored pose. The verified v2.1.2 Pose.mirror() — and this repo's RobotConstants.mirror(), correctly — use normalizeAngle(π − heading()). These are genuinely different transforms, not just a different axis-length convention as Landmine 1 originally described. The shipped code sidesteps this correctly by never calling PoseFactory at all, but the audit trail didn't know that was necessary — it got the right answer without the right reason. Anyone reaching for PoseFactory.mirrorX() directly in the future, trusting that only the axis argument needs adjusting, will get a heading rotated 180° from the correct v2-equivalent mirrored heading.

Finding E — the tuning procedures existed but were never wired up to run

MecanumTuner, PinpointTuner, and ForesightTuner in pedro/procedures/ are plain classes with no @Autonomous/@TeleOp annotation — v3's tuning framework doesn't use the Driver Station opmode list at all. Decompiling com.pedropathing:tuning-1.0.0 shows it auto-starts a web dashboard the moment the Robot/Control Hub boots (an app-lifecycle hook, no opmode needed), on http://<robot IP>:10158, and lists whichever procedures are registered via a static method annotated @Tuner returning a Procedure — found by scanning, the same mechanism the SDK uses for @Autonomous. Tuning.java was the empty stub (// Tuners go here) where that registration belongs, and it had nothing in it — the dashboard's tuner list would have shown zero tuners. Status: fixed — see Tuning.java below.

⚠ Finding G — near-vertical shots made the turret's aim noise-dominated, now fixed

ChatGPT's specific claim — that atan2(vShotHoriz, vShotZ) is "numerically unstable" near zero — is wrong; that call is smoothly defined everywhere, verified in Python (atan2(0, 5)=0°, atan2(0,-5)=180°, even atan2(0,0)=0°, never NaN). But pushing on why it raised that concern found a real, different bug nearby: phiShot = atan2(vShotY, vShotX) — the turret azimuth, not elevation — becomes noise-dominated specifically when the shot is nearly vertical (robot velocity nearly cancels the static shot's horizontal component — exactly the "lay-up" case the PDF itself describes as realistic). Simulated with plausible per-axis velocity noise on a small true horizontal vector: a 215-degree azimuth swing across 8 consecutive loop ticks. Right when the robot needs a near-vertical shot, the turret PID would have visibly hunted on noise. Fixed: subtractRobotVelocity now takes a previousTurretRelRad parameter and holds the last stable bearing whenever the horizontal shot vector drops below RobotConstants.SOM_AZIMUTH_HOLD_THRESHOLD_IN_PER_SEC (10 in/s, a soft safety margin, not a measured constant) — azimuth barely matters physically once a shot is nearly vertical anyway. 2 new tests confirm both the hold and that it doesn't trigger above threshold; 27/27 tests pass.

Unlike earlier passes (which reviewed the doc's own prior claims), this pass re-read the actual current Shooter.java/RobotConstants.java/ShooterTeleopBase.java from scratch, independently re-derived the Huskie Physics equations against subtractRobotVelocity line-by-line (no discrepancy found beyond Finding G, already fixed), then sent the same three files to GPT-4o with one candidate finding and an open-ended request to hunt for anything else. All three findings below are now fixed, compiled clean, and the full 27-test suite still passes.

⚠ Finding H — ADJUSTABLE mode silently used the opposite turret-tick sign convention from every other mode

Every other conversion of a turret angle to ticks in this codebase negates first: Shooter.setLockedMode (-lockedTurretDeg * TICKS_PER_DEGREE), Shooter.calculateTurretTarget (-lastTurretRelDeg * TICKS_PER_DEGREE), and ShooterTeleopBase.handleModeSwitch() entering FULL_MANUAL. But entering ADJUSTABLE, six lines later in the same method, had no negative sign — the opposite convention. Dormant today because RobotConstants.lockedTurretDeg = 0.0, but the instant a team sets a nonzero locked/home angle, switching into ADJUSTABLE would aim the turret at the mirror-image angle of every other mode. Traced to the original 641WinterHavenEdition-master source (ShooterTeleopBase.java and all four legacy teleop copies) — this is a pre-existing v2 bug that survived the port faithfully, not something the migration introduced. ChatGPT's independent read of the same three files agreed it was real without being led there. Fixed: both branches now use Math.round(-lockedTurretDeg * TICKS_PER_DEGREE), matching every other call site (also fixes a truncation-vs-rounding mismatch on the same two lines — up to ~0.23° of bias, cosmetic but inconsistent). Not fixed in the original v2 repo, which isn't the one being built.

Finding I — dead field turretPhysicalOffset, never wired up in either codebase

Shooter.turretPhysicalOffset was declared, defaulted to 0, and never read or written anywhere in this class or ShooterTeleopBase — a plausible calibration hook that looked like it was forgotten during migration. Checked against the original: it was never used there either, so this isn't a lost wire-up, just genuine dead code carried through two codebases. Fixed: removed rather than guessed at its intended semantics, since inventing a wiring for it risked introducing a new bug to "fix" an unused field.

Finding J — the brand-new Finding-G azimuth-hold guard had its own init-order gap

lastSomTurretRelRad (the state Finding G's near-vertical azimuth hold reads/writes) initialized to a hardcoded 0.0 rather than the turret's actual current bearing. If calculateTargetsShootOnMove's very first call ever happened to be a near-vertical shot, the hold guard would freeze the turret at field-bearing 0° instead of wherever it actually was. Low real-world stakes today since this method still isn't wired into ShooterTeleopBase (see Finding B/"not yet calibrated" below), but worth closing before whoever flips that switch inherits it. Fixed: a one-time somTurretRelRadInitialized flag now seeds lastSomTurretRelRad from the already-tracked lastTurretRelDeg (populated by any prior calculateTurretTarget/calculateTargets call) the first time the method runs, instead of trusting the field's compile-time default.

The missing translation layer, now filled in

The static shot map (flywheelSpeed(dist), hoodAngle(dist)) outputs raw actuator units — flywheel TPS, hood servo position — never a physical launch speed or angle. The PDF's vector math needs physical units to do the subtraction. Four new conversion functions in Shooter.java bridge that gap: flywheelTpsToLaunchSpeed / launchSpeedToFlywheelTps (Equation 5: v = π(R1+R2)·RPS·efficiency) and hoodPosToLaunchAngleDeg / launchAngleDegToHoodPos (linear interpolation over the hood's measured angle range). Each pair is a verified exact inverse of the other — see ShooterSomMathTest's round-trip tests.

⚠ This codebase's own data disagrees on which corner is blue vs red

The code-explained doc says (0,0) is "one corner" of the 144"×144" field, but never says which — and nothing else in the repo says either. Two existing constants point opposite directions: blueGoal = (5.0, 140.0) — very low x — suggests low-x is blue's side. But redReset = (9.0, 9.0) — also very low x — is red's own pose, suggesting the opposite. Both can't be true under a simple "blue side is low-x" rule; either redReset is deliberately far from red's own corner for some tactical reason, or the mapping is simply wrong somewhere. Nothing in the source resolves which, and getting it wrong doesn't throw an error — it just makes the robot confidently mislocalized for the whole match.

BlueAudienceCornerTeleop.java (new) is the same thin-subclass pattern as the other four teleops — but its startPose is RobotConstants.blueAudienceCornerPose_UNVERIFIED, deliberately set to (-1,-1), a coordinate outside the field's valid 0–141.5 range. That's on purpose: an out-of-bounds sentinel fails obviously (Pedro will reject or visibly mis-track it) instead of a plausible-looking wrong number quietly sending the robot off in the wrong direction all match. Fill in the real pose once it's verified against the physical field — easiest way once Saturday's Pinpoint tuning is done: place the robot at the actual corner, check the live pose in telemetry, and copy those numbers in.

⚠ Landmine 1 — Pose.mirror() unit mismatch

Pose.mirror() doesn't exist in v3. v2.1.2's formula (verified from source): fieldLength - x where fieldLength = 141.5 (the full field length). v3's closest equivalent, PoseFactory.mirrorX(axis), computes 2*axis - x — its axis parameter is half the field (the centerline), not the full length. Calling PoseFactory.mirrorX(141.5) as a drop-in replacement doubles the mirror offset. RobotConstants.java below sidesteps this by porting v2's exact formula directly, not using PoseFactory.

⚠ Landmine 2 — manual drive defaults to robot-centric

All four original teleops call setTeleOpDrive(y, x, turn, false) — verified from v2.1.2 source, isRobotCentric=false means the robot has been driving field-centric the whole time. v3's follower.manual(...) hardcodes robot-centric internally (drivetrain.drive(powers, true), no way to pass a flag). A naive translation silently flips this — the driver would feel stick-forward mean "robot's front" instead of "away from me," reversing depending on which way the robot faces. Fixed in ShooterTeleopBase.java below by pre-rotating stick input through the verified ManualDrive.fieldCentric(...) helper before calling manual().

⚠ Landmine 3 — Timer renamed, found during the ChatGPT review pass

Every one of the 6 autonomous files uses com.pedropathing.util.Timer (singular "util") for state-machine timing — pathTimer.resetTimer(), .getElapsedTimeSeconds(), etc. That whole package is gone in v3 (confirmed 404 on the current tree); it moved to com.pedropathing.utils (plural), and the method names changed too: resetTimer() → reset(), getElapsedTimeSeconds() → seconds(), getElapsedTime() → nanoseconds() (verified against v2.1.2 source vs. javap on the real v3 class). Not yet fixed in code — no auto file has been ported yet — but confirmed and queued as the first item to fix, since it needs zero hardware. The pattern worth noticing: both landmines found before this one lived in exactly the two files already translated (Pose, Follower). Nothing said the untouched files were landmine-free — they just hadn't been looked at.

Also checked, no landmine found

The ChatGPT review's top priority: audit the concrete Drivetrain/Localizer implementations before trusting Constants.create()'s eventual shape.

Decompiled revhub-3.0.0.aar (not yet opened before this review): new Mecanum(HardwareMap, MecanumConfig) and new PinpointLocalizer(HardwareMap, PinpointConfig) are both plain constructors matching exactly what the MecanumTuner/PinpointTuner procedures already generate. Foresight implements Algorithm follows the same config-object pattern, and its internal use of utils.Timer independently confirms Landmine 3's package location. So the eventual Constants.create() is now fully sketchable and low-risk, even with the hardware-specific values still blank:

public static Follower create(HardwareMap h) {
    return new Follower(
        new PinpointLocalizer(h, /* PinpointConfig from PinpointTuner's output */),
        new Mecanum(h, /* MecanumConfig from MecanumTuner's output */),
        new Foresight(/* ForesightConfig from ForesightTuner's output */)
    );
}

Also fully resolved this pass (was previously an inference, not yet confirmed): the manual()-before-update() loop order in ShooterTeleopBase.java. Read the complete body of v3's Follower.update(double) — the mode switch that applies drive power genuinely lives inside it, and manual() itself only records state. Calling update() first (the old v2 order) would apply last tick's stick input, one frame stale, every loop. No longer on the open-questions list.

⚠ Landmine 5 — found while porting PollenTrack: wrong drive-centricity mode

PollenTrack's tracking-drive branch called setTeleOpDrive(forwardPower, 0.0, turnPower, false) — the same field-centric flag as every other teleop's manual stick-driving. That's wrong specifically for this branch: forwardPower/turnPower come from the Limelight's tx (a robot-mounted camera's own offset angle) and a steering PID driving that toward 0 — an inherently robot-relative command ("turn until the ball, as the camera sees it relative to the robot's own facing, is centered"). Field-centric mode would have rotated that command by the robot's current field heading before applying it, so the robot would drive toward field-absolute "forward" instead of toward the locked ball the moment its heading differed from 0 — a pre-existing v2 bug, unrelated to the version migration, only surfaced because translating isRobotCentric's exact meaning required reading it that carefully. Fixed: the tracking branch now calls follower.manual(forwardPower, 0.0, turnPower) directly, no fieldCentric() wrapping — v3's manual() is robot-centric by construction, which is exactly what this branch always needed. The manual stick-driving branch still gets the fieldCentric() wrapper, since that part was correct in the original.

Preparing the Limelight — Hive-Vision setup

Pulled from Hive-Vision's own README (github.com/sidhuharjas/Hive-Vision, fetched live) and Limelight's official docs for the 3A specifically — not from general Limelight knowledge, since the 3A differs from older Limelights in a way that matters here (see step 5). This doesn't need Saturday's robot-driving tuners and can be done any time, on its own.

Model file to use — do not grab the wrong one

Hive-Vision ships several model files and only one is correct for a Limelight 3A. The repo's own README is explicit about this: best.onnx and best.pt are for a PC/Jetson running ONNX Runtime, not a Limelight — "no Limelight runs ONNX." The float32 best_limelight3a_float32.tflite is a PC-side verification artifact only — the 3A's neural detector will not load it (it needs full-INT8). The one file that actually goes on the robot's Limelight 3A is:

yolo/weights/best_limelight3a_ssd_mobilenetv2_300x300.tflite + yolo/weights/labels.txt

This is an SSD-MobileNetV2 model retrained specifically for the 3A's required TFLite_Detection_PostProcess contract (uint8 300×300 input, float32 outputs) — a different architecture from the YOLOv8n used everywhere else in the repo, not just a re-export of it. labels.txt defines class order yellow_pollen (0), red_nectar (1), blue_nectar (2) — this is exactly why PollenTrackConstants.POLLEN_CLASS_ID = 0 means yellow, and it must stay 0 unless labels.txt is re-ordered.

1
Wire the Limelight 3A to the Control Hub.

Run a USB-C to USB-A cable from the Limelight 3A to the Control Hub's USB 3.0 port (the blue one) — per Limelight's own hardware guide, this is required, a USB 2.0 port will not give it enough bandwidth. Mount it with at least 2 screws through its M3/M4 threaded holes if it isn't already on the robot.

2
Open the Limelight's own web interface — not the FTC Driver Station.

Wait about 15–20 seconds after power-up for its status light to turn on, then either open the "Limelight Hardware Manager" desktop app and double-click the device when it appears, or open a browser and go to http://limelight.local:5801. Caveat I can't fully verify from here: Limelight's own docs describe this working when your computer is plugged directly into the Limelight over USB — I have not confirmed whether limelight.local resolves the same way once the Limelight is instead wired into the Control Hub and you're connecting over the Control Hub's WiFi. If that address doesn't load, use the Hardware Manager app instead (more reliable for finding the device either way), or fall back to browsing the Control Hub's own WiFi-Direct IP on port 5801.

3
Go to pipeline slot 0 and set its type to "Neural Detector."

The Limelight supports 10 pipeline slots (0–9); PollenTrackConstants.LIMELIGHT_POLLEN_PIPELINE = 0 means the robot code always switches to slot 0, so upload the model there specifically, not just "a" slot. In that pipeline's settings, change "Pipeline Type" to Neural Detector.

⚠ Don't skip this — the 3A can't use Google Coral

Older Limelights (1/2/3) accelerate neural networks with a Google Coral USB stick. The 3A does not support Google Coral at all — confirmed on Limelight's own hardware page. Neural Detector pipelines on a 3A run in CPU mode instead. In the pipeline's runtime engine setting, make sure it's set to "CPU", not "Coral" — Limelight's own custom-model instructions specifically call out changing this from "coral" to "cpu" for 3A users, because trainer output defaults to Coral. If this is left on Coral, the model will not run.

4
Upload the model and labels file.

Still on the Neural Detector pipeline page, use its model upload control to upload best_limelight3a_ssd_mobilenetv2_300x300.tflite, then upload labels.txt alongside it. The Limelight will reload the pipeline after upload — give it a few seconds.

5
Point the camera at a yellow pollen ball and confirm live detection in the web UI before touching any code.

The pipeline view should draw a box around the ball labeled yellow_pollen with a confidence percentage. If nothing draws, double check step 3's pipeline type and the CPU/Coral setting above before assuming the code is broken — this step isolates whether the problem is on the Limelight side or the robot-code side.

6
Confirm the Limelight is named "limelight" in the robot's hardware configuration.

PollenTrack.java looks it up with hardwareMap.get(Limelight3A.class, "limelight") — on the Driver Station, open the active robot configuration and make sure the Limelight entry is literally named limelight (lowercase), or that line in code and the configuration will disagree and it'll fail to find the device at init.

7
Run the PollenTrack teleop and watch its telemetry, not just the robot's movement.

Hold gamepad1's right trigger (the tracking-drive trigger) and check the telemetry for detections, locked target info, and tx/ty — this confirms the FTC-side LLResult/LLResultTypes reading is actually working end-to-end, not just that the Limelight's own web UI can see the ball. PollenTrackConstants.CONFIDENCE_FLOOR = 45.0 is a second, separate confidence filter applied in robot code on top of whatever the Limelight itself reports — if detections show in the Limelight UI but never register in telemetry, check that filter and the ARRIVED_AREA/ARRIVED_TX_TOLERANCE_DEG field comment's note to tune those two from real field telemetry, same as it says.

⚠ Landmine 4 — found while porting the autos: two active bugs in Blue_15Ball_lastrow

Init order: the original constructs shooter = new Shooter(hardwareMap, follower, telemetry) before follower = Constants.createFollower(hardwareMap) runs. Shooter stores that reference in a final field — it would have permanently captured null, guaranteeing an NPE the moment Constants.create() stops being a stub. Fixed by reordering (matches every other ported file already).

Redundant, overriding control: the original calls its own coarseAlignTurret() every loop, then shooter.driveTurret() immediately overwrites its output — so that entire computation had zero effect on the robot. Same story for the flywheel: shooter.driveFlywheels(true) runs, then a separate hardcoded-1500-TPS PID overwrites it via a direct setPower() call. Same underlying category as the flywheel bug already fixed in Blue_18Ball.java, just shaped as compute-then-overwrite instead of never-called. Fixed the same low-risk way two sibling files already do elsewhere in this codebase: call sites commented out, methods left in place, not deleted.
